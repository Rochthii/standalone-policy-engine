# Odoo 17 Real-Boundary E2E Evidence — 2026-09-12

## Scope

This record covers the repository-owned Odoo PEP crossing the real process,
network and storage boundary:

`Odoo 17 ORM -> generated Python gRPC client -> mutual TLS -> Go PDP -> PostgreSQL 15`

It covers single-PDP mTLS transport and does not cover multi-replica revocation,
remote CI execution or production-path load.

## Result

Before Odoo startup, the runner verified both sides of the transport boundary:

1. a TLS client trusting the CA but presenting no client certificate was rejected during the handshake;
2. a valid client certificate paired with the wrong expected server name was rejected;
3. the valid Odoo client certificate passed hostname/chain verification and reached the JWT boundary, where a request without a Bearer token was rejected.

The addon then installed in the fresh database and all seven post-install transaction
cases passed over mTLS:

1. ALLOW performs one native purchase confirmation and an exact retry does not duplicate the attempt.
2. `REQUIRE_HUMAN_APPROVAL` persists `to approve`, one Activity and one completed attempt without rollback.
3. SoD hard deny rolls back the protected mutation, nonce and attempt.
4. A real unreachable TCP endpoint fails closed without consuming the nonce.
5. A live authenticated `RevokeDelegation` call causes the subsequent protected action to deny.
6. A proof signed with the wrong secret is rejected by the live PDP and rolls back.
7. Reusing a completed nonce for another purchase order fails closed and does not create a second attempt.

The runner then opened two independent Odoo/PostgreSQL sessions against one
purchase order. Both reached the row lock together; the losing transaction
received PostgreSQL `SerializationFailure` and was retried through Odoo's
standard `odoo.service.model.retrying` wrapper. The final database state was one
nonce, one `executed` authorization attempt and one confirmed purchase order.
